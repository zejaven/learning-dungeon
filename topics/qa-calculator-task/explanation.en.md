# Задача: протестируй калькулятор

«Простой калькулятор» — одна из самых известных задач на собеседованиях QA
джун-уровня. Условие намеренно примитивное, потому что проверяется не знание
математики, а **системность мышления**: умеет ли кандидат уточнять требования,
строить проверки по структуре, обосновывать выбор значений и не забывать про
UI и платформу. Интервьюер оценивает ответ по чек-листу «хорошо/плохо» —
ниже эталонный разбор именно по этим критериям.

## Условие

- Калькулятор, который **только складывает**.
- На вход — **целые числа от -99 до +99**.
- **Кликабельная кнопка «равно»**.
- **Поле вывода** для ответа.
- Задача: написать проверки для этого функционала. Пример: 4+5=9.

## Шаг 0: уточняющие вопросы

Первое, что оценивается, — задаёт ли кандидат вопросы, когда требования не
озвучены явно. Минимальный набор:

- **Где работает приложение?** Веб (какие браузеры?), мобильное (iOS/Android),
  десктоп? От ответа зависят кроссплатформенные проверки.
- **Как вводятся числа?** Только кнопками калькулятора или можно печатать с
  клавиатуры? Если клавиатура — появляются проверки невалидного ввода.
- **Что происходит при вводе за границами диапазона?** Блокировка ввода,
  обрезание, сообщение об ошибке?
- **Что должно происходить при невалидном вводе** (дроби, буквы, спецсимволы):
  поле не принимает символ или показывает ошибку?
- **Есть ли ограничение на результат?** Сумма двух максимальных значений
  (99+99=198) выходит за рамки входного диапазона — как отображается?

Даже если интервьюер отвечает «придумайте сами», сам факт вопросов засчитывается
в плюс — это критерий «хорошо» из условия.

## Эталонная структура проверок

### 1. Позитивные проверки (всегда первыми)

- Базовый сценарий из примера: **4+5=9** — функция делает то, для чего создана.
- Сложение двузначных чисел: 25+30=55.
- Сложение с отрицательными: -5+3=-2; 5+(-3)=2; -5+(-3)=-8.
- Ноль как операнд: 0+5=5, 5+0=5, 0+0=0.

Почему позитив первым: если сложение не работает в основном сценарии, проверять
устойчивость к мусору бессмысленно — функционал не готов. Кандидат, начинающий
с -100 и +100, показывает, что мыслит «краевыми случаями», а не рисками.

### 2. Граничные значения и классы эквивалентности

Границы заданы требованием (-99..+99), поэтому проверяются сами границы и
окрестность за ними:

- **-99, +99** — допустимые граничные значения: 99+1=100, -99+(-1)=-100.
- **-100, +100** — первые значения за границей: ввод должен быть невозможен или
  отклонён.
- **99+99=198** — максимальный результат: выходит за «двузначность» входа,
  проверяем, что поле вывода его вмещает и показывает корректно.

Классы эквивалентности для входа: отрицательные / ноль / положительные — из
каждого класса достаточно одного-двух представителей (см.
[техники тест-дизайна](topic:qa-test-design)).

### 3. Негативные проверки (невалидный ввод)

- Дроби: 2.5+3 — поле не принимает точку или выдаёт понятную ошибку.
- Буквы: латиница и кириллица (abc, абв).
- Спецсимволы: !@#%, пробелы, знаки операций (+, - в середине числа).
- Пустое поле: нажать «=» без ввода одного или обоих операндов.
- Очень длинный ввод (если ввод с клавиатуры возможен).

**Важно:** невалидные данные проверяются **по одному полю за раз** — сначала
первое поле с мусором при валидном втором, потом наоборот. Проверка
«дробь + дробь» плохая: если она падает, непонятно, какое из двух полей
обработано неверно — это два дефекта, склеенных в один кейс.

### 4. UI: кнопка «равно» и поле вывода — отдельные блоки

Частая потеря баллов: кандидат проверяет только ввод цифр, а про кнопку и поле
вывода молчит. Они — отдельные элементы функционала из условия:

- **Кнопка «равно»:** кликабельна (визуально и физически), реагирует на клик
  (состояние нажатия), не «залипает», повторное нажатие не ломает результат.
- **Поле вывода (отдельно от правильности цифры!):** результат отображается,
  не обрезается, читаемый шрифт и выравнивание; минус у отрицательного
  результата виден целиком; длинный результат (4 символа, см. ниже) помещается;
  поле очищается/обновляется при новом вводе.

### 5. Кроссплатформенность

Явно проговорить: проверки прогоняются на всех целевых платформах/браузерах
(Chrome, Firefox, Safari; iOS/Android — если мобильное). Даже если платформа не
уточнена, фраза «добавил бы кроссбраузерные/кроссплатформенные проверки»
засчитывается в плюс.

## Критерии оценки: хорошо / плохо

**Хорошо (за это плюсуют):**

- кандидат уточняет требования, если они явно не озвучены;
- начинает с позитивных проверок;
- в ответе есть структура и логика (позитив -> границы -> негатив -> UI);
- для конкретных значений есть обоснование («99 — верхняя граница из
  требований, 100 — первое значение за ней»);
- проверки по смыслу не повторяются (нет пяти вариантов «два положительных
  числа»);
- уточняет платформу или явно озвучивает кроссплатформенные/кроссбраузерные
  проверки;
- помимо валидных данных проверяются невалидные: дроби, спецсимволы, латиница,
  кириллица;
- есть отдельный блок проверок на поле вывода — без привязки к тому, что цифра
  правильная.

**Плохо (за это минусуют):**

- кандидат начинает с негатива, часто именно с -100 и +100;
- перебирает значения без системы («а давайте 7+8, а ещё 12+15…»);
- явно не проверяет кнопку «=»;
- проверяется только ввод цифр;
- в поле вывода проверяется только правильность цифры — или поле вывода вообще
  не озвучивается.

## Неочевидные детали, за которые плюсуют

**3 символа на ввод против 4 на вывод.** На вход можно ввести максимум 3 символа:
две цифры и знак «-» (-99). А в поле вывода может оказаться 4 символа: три цифры
и знак «-» (-99+(-99)=-198). Кандидат, который заметил эту асимметрию, показал,
что думает о результате, а не только о входе: поле вывода надо проверять на
более длинной строке, чем поле ввода.

**Единственная проверка в прод.** Вопрос: «Если функционал катится в прод, а
сделать можно всего одну проверку — какую?» Хороший ответ: **позитивная, как в
примере — 4+5=9**. Логика: одна проверка должна подтвердить, что функция вообще
выполняет своё назначение; граничный или негативный кейс этого не доказывает.
Любой другой вариант должен быть очень убедительно обоснован.

**X+0 — плохая проверка** (как единственная). Прибавление нуля не меняет число:
функция «сложения» фактически не проверяется — правильный ответ может выдать и
сломанная функция, которая просто возвращает первый операнд.

**-1, 0, 1 — зависит от обоснования.** Если кандидат проверяет их «как граничные
значения» — плохо: в требованиях нет границ в этой точке, граница одна и она на
±99. Если же он говорит «это границы между классами эквивалентности:
отрицательные / ноль / положительные» — это корректное применение техники,
ок. Тот же набор чисел, разная оценка: ценится обоснование, а не сами значения.

**«Дробь + дробь» — плохо.** Невалидные данные в обоих полях сразу — два
дефекта в одном кейсе; при падении непонятно, какое поле виновато. Сначала
одно поле с невалидными данными при валидном втором, потом отдельно другое.

> **Ответ на собесе за 60 секунд**
> «Сначала уточню требования: платформа, способ ввода, поведение за границами
> диапазона. Затем проверки по структуре. Позитив: 4+5=9, двузначные,
> отрицательные операнды, ноль. Границы: -99 и +99 — из требований, -100 и
> +100 — за границей, ввод должен блокироваться; 99+99=198 — проверяю, что
> поле вывода вмещает результат. Негатив: дроби, латиница, кириллица,
> спецсимволы, пустое поле — по одному полю за раз. Отдельно кнопка "равно":
> кликабельность, повторные нажатия. Отдельно поле вывода: не обрезанность,
> видимость минуса, очистка — на входе максимум 3 символа, на выводе может
> быть 4. Плюс кроссбраузерные/кроссплатформенные проверки. Если бы была
> только одна проверка перед продом — позитивная 4+5=9».

**Чем этот ответ сильный:** видна система (порядок блоков не случаен), каждое
значение обосновано, UI-элементы из условия проверены поимённо, а неочевидные
детали (3 vs 4 символа, одна проверка в прод) показывают глубину.

**Типовые ошибки кандидата** повторяют критерии «плохо»: старт с -100/+100,
перебор значений без системы, молчание про кнопку «=», проверка поля вывода
только на правильность числа и проверки без обоснования («ну проверю -1, 0, 1 —
все так делают»).
