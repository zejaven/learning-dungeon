# Проверка упражнений с кодом: пилот на collections-streams

Задача: `dungeon-verify-code-exercises`. Модуль `collections-streams`: 15 тем, 113 упражнений
(86 `predict_output`, 27 `spot_bug`). Дата: 2026-11-10.

## Как проверялось

1. **Запуск** (`ExerciseRunCheck`, лимиты ИИ не тратит). Каждый сниппет оборачивается в `Main`:
   импорты `java.util.*`, классы выносятся наружу, методы делаются `static`. Затем он дважды
   запускается на JDK 21. У `predict_output` вывод сравнивается с текстами вариантов ответа.
2. **Независимая проверка Codex** (`tools/verify/check_exercises_codex.py`, `gpt-6.1-sol`,
   reasoning high, по вызову на тему). Codex видит вопрос, код и варианты **без** отметки
   правильного, а у запускаемых ещё и реальный вывод. Сначала он отвечает сам, потом выбирает
   вариант.
3. **Разбор каждого расхождения.** Спорные места про устройство `HashMap` проверены отдельными
   программами на JDK 21 с доступом к внутренностям через `--add-opens`. Решения не опираются
   ни на урок, ни на Codex, ни на память.

Калибровка до основного прогона: на копии `hashmap` с испорченным ключом оба этапа поймали
подмену.

## Главная находка: ошибка в материале темы, а не в упражнениях

4 из 7 ошибок сидят в одной теме, `bucket-data-structure`, и все они следствие того, что сама
теория пересказывала популярное заблуждение. Проверено на JDK 21.0.11:

- **Дерево появляется на 9-й записи**, а не на 8-й: проверка идёт после того, как запись
  добавлена в цепочку. Если таблица меньше 64 корзин, 9-я запись вызывает ресайз.
- **`remove()` не превращает дерево обратно в список при 6 записях.** Решает форма дерева, и
  точный момент плавает, обычно где-то между 6 и 2 записями. `UNTREEIFY_THRESHOLD = 6`
  срабатывает только при разделении корзины на ресайзе: дерево из 9 записей разделилось на 5 и 4,
  и обе части стали списками.
- **O(log n) внутри дерева есть только для ключей, которые можно упорядочить.** Корзина из 300
  записей с одинаковым хэшем: `Comparable` ключи — 27 сравнений, не-`Comparable` — 301 вызов
  `equals`, то есть O(n). Запасное разрешение ничьих по identity-хэшу годится только для
  вставки.

Исправлено по всей теме:
- `explanation.en/ru.md`;
- 5 атомов урока: `treeify-threshold`, `untreeify-hysteresis`, `comparable-tiebreak`,
  `treeify-is-a-guardrail` и итоговый атом. Изменено около 170 строк, все id упражнений
  сохранены, поэтому прогресс не сброшен;
- вопрос Boss Fight `untreeify-threshold`;
- модель Playground `visual/VisualBucket` (дерево на 9-й записи, обратное превращение по форме,
  тест закрепляет обе границы);
- примеры и миссии.

Пилот проверял только упражнения с кодом, а это заблуждение нашлось потому, что упражнения с
кодом его задели. Остальные типы упражнений (выбор, верно/неверно, пропуски, пары) и теорию эта
проверка не ловит.

## Проверять ли остальные модули

**Да, но не все подряд, а начиная с тем про внутреннее устройство JDK.** Доля ошибок 6% —
многовато для материала, который потом закрепляется повторением. И главный ущерб был не в одном
неверном ключе, а в целой теме, построенной на заблуждении.

- Этап запуска бесплатный и занимает несколько минут на модуль. Его стоит прогнать по всем.
- Codex — один вызов на тему, это примерно 270 вызовов на все темы с уроками.
- Порядок: темы, где популярные упрощения расходятся с реальным JDK: конкурентность и Virtual
  Threads, память, GC и рефлексия, внутренности коллекций. Потом остальное.
- Отдельно стоит подумать о проверке теории (`explanation`) против реального поведения. Здесь
  ошибка шла именно оттуда.

## Как запустить на другом модуле

```
.\gradlew.bat :backend:test --tests "*ExerciseRunCheck" -Dverify.module=<id модуля из roadmap.json>
python tools/verify/check_exercises_codex.py backend/build/exercise-verify/<id модуля>
```

Отчёт со списком всего, что нужно разобрать: `backend/build/exercise-verify/<id модуля>/report.md`.
Codex с аккаунтом ChatGPT принимает только модели из `~/.codex/models_cache.json`, остальные
отклоняются с ошибкой «not supported when using Codex with a ChatGPT account». Модель можно
задать флагом `--model`.
