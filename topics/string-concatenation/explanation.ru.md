# Конкатенация миллиона строк

## Интуиция

Представьте, что вы пишете один длинный список гостей, по одному имени за раз. С
оператором `+` в цикле в Java это выглядит так, будто каждый раз, добавляя имя, вы
берёте **чистый лист бумаги, переписываете все уже внесённые имена, а затем
дописываете новое** — а старый лист выбрасываете в корзину. К тысячному имени вы
переписываете список из тысячи строк ради одного слова. Корзина переполняется
выброшенными листами.

Именно это и делает `result = result + piece`. Поскольку строка в Java
[иммутабельна](topic:string-immutability), её нельзя изменить на месте. Каждый `+`
выделяет **совершенно новую** строку, копирует **все** накопленные символы,
дописывает новый кусок и оставляет предыдущую строку мусором. Добавление куска
номер *k* копирует примерно *k* символов, поэтому сборка *n* кусков стоит
`1 + 2 + … + n ≈ n²/2` копий символов. Для миллиона кусков это порядка **полутриллиона**
копирований и миллион мёртвых объектов — та самая ловушка по памяти, о которой
спрашивают.

`StringBuilder` — это вариант с **маркерной доской**: одна поверхность для записи,
которую вы продолжаете дописывать. Каждый `append` записывает только новый кусок на
**ту же** доску — без переписывания, без выброшенных листов. Работа пропорциональна
итоговой длине: O(n), а не O(n²).

```mermaid
flowchart TD
  subgraph CONCAT["result = result + piece  (O(n^2))"]
    A1["new String"] --> A2["скопировать ВСЕ символы"]
    A2 --> A3["старая String становится мусором"]
    A3 --> A1
  end
  subgraph BUILD["StringBuilder.append  (O(n))"]
    B1["один буфер char[]"] --> B2["скопировать ТОЛЬКО новый кусок"]
    B2 --> B1
  end
```

## Как на самом деле работает StringBuilder

`StringBuilder` оборачивает один изменяемый буфер `char[]` с **ёмкостью** по
умолчанию 16. `append` копирует новые символы в свободное место этого буфера — как
запись на пустой части доски. Когда буфер заполняется, он **растёт**: выделяется
больший массив (`(capacity << 1) + 2` в JDK — примерно удвоение), накопленные
символы один раз копируются туда, а старый массив выбрасывается. Это тот же приём
амортизированного удвоения, что использует [ArrayList](topic:arraylist-internals).

Удвоение важно: буфер с удвоением достигает миллиона символов примерно за 20 шагов
роста, и суммарная работа по копированию при росте всё равно лишь ~2n. Это как
покупать вдвое большую доску каждый раз, когда место кончается, — вы меняете доску
всего несколько раз, а не на каждом имени.

```mermaid
flowchart LR
  S["ёмкость 16"] -->|"заполнен"| G1["рост -> 34"]
  G1 -->|"заполнен"| G2["рост -> 70"]
  G2 -->|"заполнен"| G3["рост -> 142 ..."]
  G3 --> D["всего O(log n) ростов"]
```

Если итоговый размер можно оценить, **задайте размер заранее** через
`new StringBuilder(expectedSize)`. Тогда массив выделяется один раз, достаточно
большой для всего, и **никогда не растёт** — ноль перевыделений, ноль мусорных
буферов. Это как сразу забронировать зал нужного размера для свадьбы, а не
переселять всех в больший зал три раза за ужин.

## Ответ за 60 секунд на собеседовании

> Никогда не собирайте большую строку через `+` (или `+=`) в цикле. Так как
> `String` иммутабелен, каждый `+` создаёт новую строку и копирует все накопленные
> символы, поэтому цикл имеет сложность O(n²) по времени и плодит O(n) мусорных
> объектов — это и есть проблема памяти при конкатенации миллиона строк. Используйте
> `StringBuilder` (или `StringBuffer`, если нужна потокобезопасность): он держит
> один изменяемый буфер `char[]`, `append` копирует лишь новый кусок, а буфер растёт
> удвоением, так что всё целиком O(n). Если я знаю примерный итоговый размер, я задаю
> его через `new StringBuilder(capacity)`, чтобы избежать даже копий при росте. Для
> склейки готовой коллекции я бы взял `String.join` или `Collectors.joining`,
> которые внутри используют `StringBuilder`.

## Где это важно в продакшене

- Сборка строк CSV/JSON/SQL/логов в цикле — классическое место, где это бьёт; разница
  между `+` и `StringBuilder` на больших входах — это разница между секундами и
  миллисекундами и между тяжёлым давлением на GC и почти полным его отсутствием.
- Выброшенные объекты `String` накапливаются в молодом поколении и вызывают частые
  сборки мусора — см. [Поколения кучи JVM](topic:heap-generations). Меньше мусора —
  меньше пауз GC.
- Предварительный размер буферов (и коллекций) — дешёвая и высокоэффективная
  оптимизация на горячих путях, где размер можно оценить.

## Частые заблуждения и ловушки

- **«`+` всегда плохо.»** Нет. Одиночное выражение вроде `a + b + c` нормально —
  **компилятор** сам превращает его в один `StringBuilder`. Ловушка — это `+`
  **внутри цикла**, где каждая итерация это отдельное выражение и получает свою новую
  строку. Компилятор не может вынести билдер за пределы цикла за вас.
- **«`StringBuilder` и `StringBuffer` — одно и то же.»** `StringBuffer` — это
  более старая, синхронизированная (потокобезопасная) версия, и она немного
  медленнее; используйте `StringBuilder`, если только один билдер действительно не
  разделяется между потоками.
- **«Предварительный размер почти не помогает.»** На больших входах он убирает
  каждый шаг роста с копированием и промежуточные мусорные массивы — это измеримо на
  горячих путях.
- **«Конкатенация в цикле просто некрасива.»** Это не только стиль: она меняет
  сложность с O(n) на O(n²). На миллионе кусков это разница между завершением и
  фактическим зависанием.
- **`String.format` тоже не инструмент для быстрого цикла** — он разбирает строку
  формата на каждом вызове. Для повторяющихся дописываний выигрывает `StringBuilder`.
