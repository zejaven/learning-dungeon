# Задача: найди ошибки в JSON

Популярная практическая задача на собеседованиях QA: интервьюер показывает
кусок «конфигурации» в формате JSON и просит найти ошибки. Проверяется
не умение программировать, а **внимательность и знание спецификации** — JSON
тестировщик видит каждый день в ответах API, и человек, который не замечает
битый JSON, будет пропускать баги в интеграциях. Вторая проверяемая вещь —
зрелость: кандидат должен отличать «синтаксически невалидно» от «валидно, но
подозрительно».

## Условие задачи

Найдите ошибки в блоке конфигурации (все ошибки посажены намеренно, формат
приближен к исходному заданию):

```json
{
  "block_id": 73bf37d59d,
  "type": "title_text",
  "padding_top": 01,
  "padding_bottom": 0,
  "configurations":
  [
    {
      "priority": "0",
      "conditions": [],
      "options":
      {
        "title": "Сервисы и приложения",
        "title_font_size": 20,5
        title_font_style : null,
        "has_light_background": "false",
        "value":
        [
          "mobile",
        ],
        "items":
        [
          {
            "type": "simple",
            "title": "Кино и ТВ"
        ],
      }
    }
  ]
},
```

## Эталонный разбор: ошибка -> почему невалидно -> как исправить

| # | Место | Ошибка | Почему невалидно | Как исправить |
|---|---|---|---|---|
| 1 | `"block_id": 73bf37d59d` | Значение без кавычек | `73bf37d59d` — не число и не литерал `true/false/null`; произвольный идентификатор в JSON не существует | Взять в кавычки: `"block_id": "73bf37d59d"` |
| 2 | `"padding_top": 01` | Ведущий ноль в числе | Спецификация запрещает числа с ведущими нулями: после `0` не может идти другая цифра | `1` — если нужно число, `"01"` — если важна строка |
| 3 | `"title_font_size": 20,5` | Запятая вместо точки в числе | Дробная часть отделяется только точкой; парсер прочитает `20`, а дальше сломается | `20.5` |
| 4 | Строка с `20,5` | Нет запятой в конце строки | После значения перед следующим ключом обязательна запятая | Добавить запятую: `"title_font_size": 20.5,` |
| 5 | `title_font_style : null` | Ключ без кавычек | В JSON все ключи — строки, а строки — только в двойных кавычках (в отличие от JS-объектов) | `"title_font_style": null` |
| 6 | `"value": [ "mobile", ]` | Висячая запятая в массиве | После запятой парсер ждёт следующий элемент, а находит `]` | Убрать запятую: `[ "mobile" ]` |
| 7 | `items: [ { ... "title": "Кино и ТВ" ]` | Незакрытая фигурная скобка объекта внутри массива | Объект `{` не закрыт, `]` закрывает массив раньше времени — структура разваливается | Добавить `}` после `"title": "Кино и ТВ"`, затем `]` |
| 8 | Запятая после `]` массива `items` | Лишняя запятая | После `items` в объекте `options` больше нет ключей — запятой быть не должно | Убрать запятую |
| 9 | `},` в самом конце | Висячая запятая на верхнем уровне | Запятая нужна, только если объект — элемент массива и за ним следует ещё элемент; здесь это корневой объект | Убрать запятую (либо показать продолжение массива) |

**Валидно, но подозрительно (это не ошибки, но отметить стоит):**

- `"has_light_background": "false"` — синтаксически валидно (строка), но почти
  наверняка задумывалось булево `false` без кавычек. Если код сравнивает значение
  как булево, непустая строка `"false"` будет истинной — классический источник
  багов. На собесе правильно сказать: «допустимо, но вызывает вопрос, уточнил
  бы у разработчика».
- `"priority": "0"` — число строкой. Допустимо, но стоит уточнить контракт:
  приоритет обычно число.
- `"conditions": []` — пустой массив. Полностью валидно, ошибкой не является.

## Свод правил синтаксиса JSON

- **Строки — только в двойных кавычках.** Одинарные кавычки невалидны.
- **Ключи — всегда строки в двойных кавычках.** Это главное отличие JSON от
  JavaScript-объекта, где ключи можно писать без кавычек.
- **Числа:** без ведущих нулей (`01` — ошибка), дробная часть через точку
  (`20.5`, не `20,5`), допустимы минус и экспонента (`-3, 2.5e3`).
- **Литералы:** `true`, `false`, `null` — строчными буквами и без кавычек.
  `"true"` — уже строка, а не булево.
- **Никаких висячих запятых** — ни в объектах, ни в массивах.
- **Никаких комментариев** — стандарт JSON их не предусматривает (в отличие от
  JSONC/JSON5, которые конфиги иногда используют, но это другие форматы).
- Структура — только `{}` для объектов, `[]` для массивов; скобки должны быть
  сбалансированы.

## Как валидировать на практике

- **Парсер как истина:** правило «не считаю скобки глазами». Вставить текст в
  любой валидатор/форматтер (онлайн-линтеры типа jsonlint, `JSON.parse()` в
  консоли браузера, `python -m json.tool`, `jq .` в терминале) — парсер покажет
  первую ошибку и её позицию.
- **IDE и редакторы** (VS Code, IDEA) подсвечивают синтаксические ошибки JSON
  прямо при открытии файла.
- **В тестировании API:** Postman и REST-клиенты форматируют ответ и сразу
  помечают невалидный JSON; в автотестах ответ парсится в объект — если парсинг
  падает, это уже дефект. Подробнее о работе с ответами API — см.
  [тестирование API](topic:qa-api-testing) и
  [HTTP и взаимодействие клиент-сервер](topic:qa-http-client-server-deep).
- **Важный нюанс:** валидный JSON не значит корректный. Синтаксис проверяет
  парсер, а соответствие контракту (типы полей, обязательность, значения) —
  JSON Schema и контрактные тесты. Кейс `"has_light_background": "false"` —
  ровно про это: синтаксис в порядке, а семантика сломана.

> **Ответ на собесе за 60 секунд**
> «Вижу девять синтаксических ошибок: block_id без кавычек; padding_top равен
> 01 — ведущий ноль запрещён; в title_font_size запятая вместо точки и пропущена
> запятая в конце строки; ключ title_font_style без кавычек; висячая запятая
> в массиве value; объект внутри items не закрыт фигурной скобкой; лишняя
> запятая после массива items; висячая запятая после корневого объекта. Отдельно
> отмечу: "has_light_background": "false" — валидно, но подозрительно, скорее
> всего задумывалось булево false. На практике такое не считаю глазами — прогоняю
> через парсер или линтер, а семантику проверяю по JSON Schema».

**Почему такой ответ сильный:**
- ошибки названы системно — по порядку сверху вниз, без пропусков: видно, что
  кандидат читает структуру, а не тычет наугад;
- кандидат разделяет «невалидно» и «валидно, но подозрительно» — это показывает
  опыт работы с реальными контрактами API, а не только со спецификацией;
- упомянут практический инструментарий (парсеры, линтеры, схемы), а не только
  ручной разбор.

**Типовые ошибки кандидата:**
- найти 3–4 «громкие» ошибки и остановиться, пропустив висячие запятые и
  незакрытую скобку — они менее заметны глазу;
- назвать ошибкой `"priority": "0"` или пустой массив `[]` — обе записи
  валидны, это ловушка на поверхностное знание;
- сказать «false в кавычках — ошибка»: нет, это валидная строка; правильная
  формулировка — «валидно, но семантически подозрительно»;
- не упомянуть, что JSON не терпит комментариев и одинарных кавычек — частый
  follow-up «а так можно?».
