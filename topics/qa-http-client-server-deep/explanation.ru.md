# HTTP и клиент-сервер: углублённо

После базовых вопросов про методы и статус-коды (см.
[тестирование API](topic:qa-api-testing)) интервьюер почти всегда «копает
глубже»: кто вообще может быть клиентом, из каких частей состоит запрос, как
браузер находит сервер по доменному имени и как сервер понимает, с какого
устройства вы пришли. Эти вопросы проверяют не заученные определения, а
понимание того, что реально происходит в сети, когда вы тестируете приложение.
Финал блока — две практические задачи: негативные сценарии для POST-запроса и
поиск ошибки в JSON.

## Кто может выступать в роли клиента

Клиент — это тот, кто **инициирует запрос** и потребляет ответ сервера. Роль
клиента не привязана к конкретному типу программы:

- **браузер** — самый очевидный пример;
- **мобильное приложение** — ходит на тот же бэкенд, что и сайт;
- **десктопное приложение**;
- **другой сервер** — микросервис, вызывающий соседний микросервис, для него
  является клиентом; сервер платёжного шлюза — клиент API банка;
- **скрипты и утилиты** — curl, Postman, автотест, консольная команда.

> **Ответ на собесе за 60 секунд**
> «Клиентом может быть всё, что отправляет запрос: браузер, мобильное или
> десктопное приложение, другой сервер (например, микросервис), скрипт, curl,
> Postman. Клиент-сервер — это про роли во взаимодействии, а не про конкретные
> программы: один и тот же сервер в одном запросе сервер, а в другом — клиент
> чужого API».

## HTTP и HTTPS

- **HTTP** — протокол передачи гипертекста: текстовый протокол поверх TCP,
  по умолчанию порт **80**. Данные передаются **в открытом виде** — любой
  посредник в сети может прочитать и подменить трафик.
- **HTTPS** — тот же HTTP, но поверх шифрованного канала **TLS/SSL**, порт
  **443**. Шифрование даёт три вещи: **конфиденциальность** (трафик нельзя
  прочитать), **целостность** (нельзя незаметно изменить) и **аутентичность**
  (сертификат подтверждает, что вы говорите именно с тем сервером).

Практическая деталь для тестировщика: именно поэтому сниффер (Charles, Fiddler)
для просмотра HTTPS-трафика требует установки своего корневого сертификата на
устройство — иначе трафик зашифрован и не читается.

> **Ответ на собесе за 60 секунд**
> «HTTPS — это HTTP поверх TLS-шифрования, порт 443 против 80 у HTTP. HTTPS
> даёт шифрование трафика, защиту от подмены и подтверждение подлинности
> сервера сертификатом. Сегодня HTTPS — стандарт: браузеры помечают HTTP-сайты
> как небезопасные».

## Компоненты HTTP-запроса и ответа

**HTTP-запрос** состоит из:

1. **Стартовая строка (request line)** — метод, путь, версия протокола:
   `POST /api/users HTTP/1.1`.
2. **Заголовки (headers)** — метаданные парами «ключ: значение»: `Host`,
   `Content-Type`, `Authorization`, `User-Agent`, `Accept`, `Cookie` и др.
3. **Пустая строка** — разделитель заголовков и тела.
4. **Тело (body)** — необязательная часть; данные запроса (JSON, form-data).
   Есть у POST/PUT/PATCH, обычно нет у GET/DELETE.

**HTTP-ответ** зеркален:

1. **Стартовая строка (status line)** — версия, код и текст статуса:
   `HTTP/1.1 201 Created`.
2. **Заголовки** — `Content-Type`, `Content-Length`, `Set-Cookie`,
   `Cache-Control` и др.
3. **Пустая строка**.
4. **Тело** — данные ответа (JSON, HTML, файл).

Умение «разобрать» запрос и ответ на эти части — рабочий навык: в Charles или
DevTools вы постоянно смотрите, какой заголовок ушёл, что в теле, какой
статус вернулся.

## Как браузер узнаёт, куда отправить запрос: DNS

Когда вы вводите `example.com`, браузер не знает IP-адреса этого сервера.
Прежде чем отправить HTTP-запрос, имя нужно **разрешить (resolve)** через
**DNS (Domain Name System)**:

1. Браузер проверяет свой кэш DNS и кэш ОС (файл hosts).
2. Если записи нет — обращается к DNS-резолверу провайдера/системы.
3. Резолвер при необходимости идёт по иерархии: корневые серверы → серверы
   зоны `.com` → авторитетный сервер домена.
4. Полученный IP-адрес кэшируется (на время TTL), и браузер устанавливает
   TCP-соединение (и TLS-сессию для HTTPS) с этим IP, затем отправляет запрос
   с заголовком `Host: example.com` — потому что на одном IP может жить много
   сайтов.

> **Ответ на собесе за 60 секунд**
> «Браузер преобразует доменное имя в IP-адрес через DNS: сначала смотрит в
> локальные кэши, потом спрашивает DNS-сервер. Получив IP, он устанавливает
> соединение с сервером и отправляет HTTP-запрос, в котором заголовок Host
> указывает исходный домен».

Для тестировщика это не абстракция: файл hosts и DNS-записи — стандартный
способ направить приложение на тестовый стенд, не пересобирая его.

## Как сервер узнаёт, с какого устройства вы зашли: User-Agent и другие заголовки

Сервер «видит» клиента только через заголовки запроса. Главные:

- **User-Agent** — строка, в которой клиент сообщает браузер/приложение,
  версию, ОС и устройство. Например, по ней сервер отличает iPhone от
  десктопного Chrome и может отдать мобильную версию.
- **Accept-Language** — предпочитаемые языки интерфейса (`ru-RU,ru;q=0.9,en;q=0.8`),
  по нему выбирается локализация.
- **Accept / Accept-Encoding** — какие форматы и сжатие клиент понимает.
- **Cookie** — сессия и ранее сохранённое состояние.
- **Referer** — откуда пришёл пользователь.

Важный нюанс: User-Agent — это **декларация клиента**, а не гарантия. Его
можно подменить — и это рабочая техника тестирования: переключить User-Agent
в DevTools/Charles, чтобы проверить мобильную версию сайта без телефона.

## Зачем тестировать API

Короткое обоснование (подробнее — в
[тестировании API](topic:qa-api-testing)): API тестируют, потому что баги
логики, валидации и безопасности живут на бэкенде, а UI может их маскировать;
API-тесты быстрее, стабильнее и раньше готовы, чем UI; через API проверяют
негативные и граничные сценарии, которые через интерфейс воспроизвести сложно
или невозможно.

## Параметры в GET и тело GET-запроса

Параметры GET-запроса передаются в **query string** — прямо в URL:

```
GET /api/users?role=admin&active=true
```

- после пути идёт символ **`?`** — всё, что за ним, считается GET-параметрами;
- параметры разделяются друг от друга амперсандом **`&`**;
- формат каждого — `ключ=значение`, спецсимволы кодируются (percent-encoding).

**Можно ли передать тело в GET?** Технически спецификация HTTP не запрещает
тело у GET, но его **семантика не определена**: серверы, прокси и кэши вправе
его игнорировать, многие фреймворки тело GET просто не читают. Правильный
ответ на собесе: «формально можно, но на практике не делают — тело GET
нестандартно и непредсказуемо обрабатывается; данные GET передают в query
string».

## Задача: негативные сценарии для POST, создающего пользователя

**Условие.** Есть POST-запрос, создающий нового пользователя (например,
`POST /api/users` с телом JSON: имя, email, пароль и т.д.). Сформулируйте
негативные сценарии.

**Эталонный ход рассуждений.** Негативные сценарии удобно раскладывать по
слоям запроса — так вы ничего не забудете и покажете системность:

1. **Обязательные поля**: отсутствует каждое обязательное поле по очереди;
   пустое тело; поле есть, но значение `null` или пустая строка.
2. **Валидация форматов**: невалидный email (без `@`, без домена), слишком
   короткий/длинный пароль, спецсимволы и эмодзи в имени, очень длинные
   строки (граничные значения длины ±1), числа вместо строк и наоборот.
3. **Структура JSON**: битый JSON (синтаксическая ошибка), лишние
   непредусмотренные поля, объект вместо массива, дублирующиеся ключи.
4. **Уникальность и бизнес-правила**: пользователь с таким email уже
   существует (дубликат) — ожидаем 409/422, а не 201 и не 500.
5. **Права доступа**: запрос без токена (ожидаем 401), с чужими/недостаточными
   правами (403), с протухшим токеном.
6. **Заголовки**: без `Content-Type: application/json`, с неверным
   `Content-Type` (ожидаем 415/400).
7. **Безопасность**: SQL-инъекции и XSS в строковых полях — значения не должны
   выполняться и должны корректно экранироваться.

**Чем этот ответ хорош.** Кандидат не перечисляет случайные «плохие вводы», а
идёт по структуре запроса: поля → форматы → синтаксис → бизнес-правила →
права → заголовки → безопасность. Для каждого сценария назван ожидаемый
результат (код 4xx, понятное сообщение об ошибке, отсутствие записи в базе) —
именно это отличает мидла от джуна.

## Задача: какой из двух JSON валидный

**Условие.** Даны два похожих JSON; определите, какой валидный и почему.

```json
// Первый
{
  "name": "Ivan",
  "phone": "+79001234567"
  "age": 30
}

// Второй
{
  "name": "Ivan",
  "phone": "+79001234567",
  "age": 30
}
```

**Эталонный ответ.** Валиден **второй**: в первом **отсутствует запятая**
после значения `"phone"` — пары «ключ: значение» в JSON обязаны разделяться
запятыми. Синтаксическая ошибка делает весь документ невалидным: парсер
упадёт целиком, а не «пропустит одно поле».

**Чем этот ответ хорош.** Кандидат не просто тычет в запятую, а называет
правило (разделение пар запятыми) и следствие (невалиден документ целиком).
Хороший бонус — упомянуть другие типовые ошибки JSON: висячая запятая,
одинарные кавычки вместо двойных, комментарии (в JSON их нет), и то, что
проверить валидность можно любым JSON-валидатором или парсером в Postman.

## Что хочет услышать интервьюер

- Понимание, что клиент — это **роль**, а не «браузер».
- HTTPS = HTTP + TLS, порты 80/443, что даёт шифрование.
- Запрос/ответ по частям: стартовая строка, заголовки, пустая строка, тело.
- DNS как перевод домена в IP до отправки запроса; роль заголовка `Host`.
- User-Agent и Accept-Language как источник данных об устройстве/ОС/языке —
  и что это подменяемые декларации.
- `?` начинает query string, `&` разделяет параметры; тело в GET —
  «формально возможно, практически нет».
- В задачах — **системность**: негативные сценарии слоями, с ожидаемым
  результатом для каждого.

## Типовые ошибки кандидата

- Считать, что клиент — только браузер.
- Путать HTTPS с «другим протоколом»: это тот же HTTP, но внутри
  TLS-канала.
- Говорить «браузер сам знает IP» — без упоминания DNS.
- Утверждать, что тело в GET «запрещено стандартом» (не запрещено, но
  семантика не определена и на практике игнорируется) или, наоборот, что это
  нормальная практика.
- В задаче про POST — выдавать только «пустое поле» и «невалидный email»,
  забыв про права, заголовки, дубликаты и безопасность.
- В задаче про JSON — найти запятую, но не объяснить правило и последствия.
