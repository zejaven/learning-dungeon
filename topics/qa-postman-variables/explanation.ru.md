# Postman: переменные и коллекции

Вопрос «расскажите, как вы пользовались Postman» звучит просто, но это
ловушка для тех, кто только вручную дёргал запросы. Интервьюер хочет понять
глубину: ограничились ли вы кнопкой Send, писали ли проверки ответов,
автоматизировали ли прогоны. Вторая часть блока — переменные и порядок
выполнения скриптов: это классика, которую спрашивают почти дословно.

## «Как вы пользовались Postman» — три уровня ответа

Выстройте ответ по нарастанию сложности — так видно реальный опыт:

1. **Ручное тестирование бэкенда**: собирал запросы (метод, URL, заголовки,
   тело), отправлял, смотрел статус и тело ответа; хранил запросы в
   коллекциях, сгруппированных по фичам, а не в хаотичной истории.
2. **Проверки ответов (tests)**: писал post-response скрипты (вкладка Tests)
   на JavaScript: проверка статус-кода, структуры и значений полей JSON,
   времени ответа; сохранение значений из ответа в переменные для следующих
   запросов (например, `id` созданной сущности).
3. **Автоматизация**: связывал запросы в сценарии через переменные, гонял
   коллекцию целиком через **Collection Runner** (в том числе с data-файлом
   для параметризации), выносил прогоны в CI через **Newman** — консольный
   раннер коллекций Postman.

> **Ответ на собесе за 60 секунд**
> «Начинал с ручной проверки API: коллекции запросов по фичам, разные окружения
> для стендов. Затем добавлял автопроверки: статус-код, схема и ключевые поля
> ответа в Tests. Дальше связывал запросы в сценарии через переменные и гонял
> коллекции через Collection Runner, а для регулярных прогонов — через Newman
> в CI».

## Переменные: зачем нужны

Переменная — это именованное значение, на которое ссылаются через двойные
фигурные скобки: `{{baseUrl}}`, `{{token}}`. Они решают три задачи:

- **переиспользование** — один раз задать базовый URL стенда, а не править 50
  запросов;
- **переключение окружений** — та же коллекция работает на dev, stage и prod,
  меняется только окружение;
- **связывание запросов** — ответ одного запроса (id, токен) становится
  входом следующего.

## Уровни переменных и когда какие применять

| Уровень (scope) | Область действия | Когда применять |
| --- | --- | --- |
| **Global** | весь Postman, все коллекции и окружения | значения, общие для всего: версия API, общие ключи. Использовать редко — засоряют всё |
| **Environment** | выбранное окружение (dev / stage / prod) | URL стенда, креды, токены окружения — всё, что меняется между стендами |
| **Collection** | одна коллекция | общие для запросов коллекции значения: `baseUrl` фичи, общий заголовок |
| **Local** | один запуск / один скрипт | временные значения в pre-request/tests, данные одной итерации |

(Есть ещё **data-переменные** — из CSV/JSON-файла в Collection Runner; на
собесе обычно достаточно четырёх основных уровней.)

Правило здравого смысла: значение храните на **самом узком** подходящем
уровне. Токен стенда — в окружении, а не в global; временный id — в local, а
не в коллекции.

## Приоритет при одинаковых именах

Если переменные с одним именем заданы на нескольких уровнях, **побеждает
более узкая область**:

```
local > environment > collection > global
```

То есть локальная переменная перекрывает переменную коллекции, а та —
глобальную с тем же именем. Это и удобный механизм (можно временно
переопределить значение), и источник багов: «запрос идёт не на тот стенд»
часто означает, что значение в окружении перекрыло ожидаемое глобальное.

> **Ответ на собесе за 60 секунд**
> «При одинаковых именах приоритет у более узкой области: локальная выше
> окружения, окружение выше коллекции, коллекция выше глобальной. Поэтому
> общие значения держат широко, а переопределяют точечно — более узкой
> переменной».

## Скрипты: pre-request и post-response

У каждого запроса (и папки, и коллекции) есть две точки выполнения JS-кода:

- **Pre-request script** — выполняется **до отправки запроса**: подготовить
  данные, сгенерировать токен/подпись, выставить переменные, посчитать
  timestamp.
- **Post-response (Tests)** — выполняется **после получения ответа**:
  проверки (`pm.test`, `pm.response`), сохранение полей ответа в переменные.

Важная иерархия: скрипты можно вешать на **коллекцию, папку и запрос** — и
они наследуются: скрипт коллекции выполняется для каждого запроса в ней.

**Что выполняется при запуске коллекции в первую очередь?** Pre-request
скрипты — до отправки первого запроса (включая pre-request уровня коллекции).
Тесты отрабатывают только после ответов, поэтому «вначале — тесты» — неверный
ответ.

## Автоматизация прогонов: Collection Runner и Newman

- **Collection Runner** — встроенный прогон коллекции целиком: выбираете
  окружение, число итераций, при желании CSV/JSON с данными (data-driven
  тесты), получаете отчёт по всем проверкам.
- **Newman** — CLI-раннер тех же коллекций: коллекция экспортируется в JSON и
  запускается командой `newman run collection.json -e env.json`, что позволяет
  встроить API-прогоны в CI-пайплайн (Jenkins, GitLab CI и т.д.) и получать
  отчёты.

Упоминание Newman на собесе — сильный сигнал: вы не просто «кликали в
Postman», а встраивали проверки в процесс. Связь с общей картиной
автоматизации см. в [автоматизации тестирования](topic:qa-automation).

## Что хочет услышать интервьюер

- Структурированный рассказ об опыте: запросы → проверки → автоматизация, а
  не «ну, отправлял запросы».
- Переменные — для переиспользования, окружений и связки запросов; синтаксис
  `{{var}}`.
- Чёткое знание уровней и приоритета: local > environment > collection >
  global.
- Pre-request выполняется до запроса (первым при запуске коллекции), Tests —
  после ответа.
- Collection Runner и Newman как путь к CI.

## Типовые ошибки кандидата

- Путать приоритет: считать, что глобальная переменная «главнее» локальной.
- На вопрос «что выполняется первым при запуске коллекции» отвечать
  «тесты» — тесты идут после ответа; первыми идут pre-request скрипты.
- Хранить всё в глобальных переменных — признак отсутствия опыта с
  окружениями.
- Не знать, чем environment отличается от collection variables.
- Считать, что Postman — только ручной инструмент, и не знать про Newman/CI.
